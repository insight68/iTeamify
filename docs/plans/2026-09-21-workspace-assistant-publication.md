# 新工作区助手显示与发布字段闭环

## 生产证据与原因

2026-09-21 只读检查：`auro0921` 于 08:45:18 创建，约 19.2 秒后装配完成，四个助手均为 active。首次打开时助手列表为空，客户端使用无限 staleTime；装配激活没有发送前端的 agent:created 事件，原有装配状态查询也未挂载。因此后台完成后页面仍保留空列表，强刷才重新读取。

四个源助手都有图标（两张上传图片、两个 emoji），但对应发布版本的 manifest/source_snapshot 均未记录 avatar_url，装配 SQL 也未写入该字段。缺失发生在发布和装配链路，无法靠刷新恢复。

`aurogrowth` 的 managed_smoke_failed 属于另一类真实装配失败，本次不将其当作缓存问题修复。

## 最小字段合同

| 字段 | 源助手 → 发布快照 → 蓝图 → 新助手 |
| --- | --- |
| avatar_url | 新增贯通。emoji 原样保留；图片发布为独立内容哈希路径，蓝图引用已冻结图片，新助手写入现有 avatar_url 列。 |
| name/display_name、description、instructions | 保留现有复制语义；默认模板和候选发布共用一个快照结构。 |
| model | 补齐默认模板漏项。空值沿用目标运行时默认值；显式值必须匹配来源/目标 provider 及托管模型合同，否则拒绝发布。 |
| permission_mode、invocation_targets | 保留 private 或整个工作区范围。快照不存源工作区 ID，装配时绑定目标工作区；成员/团队范围不能直接跨工作区复制，拒绝发布而非扩大权限。 |
| max_concurrent_tasks | 已贯通，保持原值。 |
| enabled skills 与 MCP profiles | 继续使用现有发布依赖闭包和凭据隔离机制，不新增第二套复制逻辑。 |
| owner_id、workspace_id、runtime_id、skill_id | 由目标工作区装配重新绑定。 |
| thinking_level、service_tier、custom_env、custom_args、runtime_config、Composio、disabled_runtime_skills | 不新增通用执行配置复制；这些值依赖目标运行时或工作区环境。 |
| status、last_seen_at、计数、归档状态、发布溯源 | 由目标生命周期生成，不复制源助手运行状态。 |

## 图片与兼容

- 使用现有 Storage；图片最大 5 MiB，PNG/JPEG/GIF/WebP，发布路径为 managed/avatars/<sha256>.<ext>。不增加数据库列或媒体框架。
- 预览只读取验证；正式发布保存独立副本。来源越权、文件不存在或保存失败会阻止发布，不能静默丢图标。
- 源工作区删除/换图不影响已发布图片；不为每个新工作区重复复制文件。
- 历史发布版本保持不可变；缺少 avatar_url 的旧蓝图继续可读，旧候选的内容哈希保持稳定。
- 旧 public_to 候选没有保存调用范围，必须重新提交；不能猜测原授权范围。
- 已有助手通过现有字段级三方差异建议选择 avatar_url；显示当前/上游图标、冲突提示，并把图标纳入并发指纹。不会自动覆盖工作区定制。

## 显示同步

激活事务提交后发送现有 agent:created 事件。Web/桌面端共享入口挂载现有装配状态查询；到达 ready 后取消激活前的在途读取，再失效助手、技能和运行时缓存。正常终态停止轮询；失败状态不会伪装成 ready。

## 验证和发布边界

回归覆盖两条发布入口、图片独立副本、模型/权限、装配隐藏到激活、头像冲突/并发修改、初始空缓存及迟到空响应。数据库测试使用独立 PostgreSQL，不启动真实模型。

上线需部署后端/Web，再经现有管理员入口从相同源助手发布新的默认模板；部署代码本身不会给旧模板补字段。最后创建新工作区，验证不刷新出现助手、图片实际可读。既有工作区的头像只通过显式字段建议应用。
