## Daemon 的主要功能

Daemon（`internal/daemon/daemon.go`）是跑在用户本机的 agent 守护进程，核心职责是把 server 派发的任务交给本地安装的 AI CLI 执行。`Run()` 方法（第 1011 行）启动后做这几件事：

**主链路（5 步任务生命周期）**：

1. **runtime 注册** — 启动时 `preflightAuth` 探测本地装了哪些 agent CLI（claude/codex/copilot 等 16+），为每个 workspace 的每个 agent 调 `client.Register()` 注册一个 runtime，server 返回 runtime_id
2. **poll 认领** — `pollLoop`（第 3066 行）→ `runBatchPoller`（第 3124 行）：先用信号量（`MaxConcurrentTasks=20`）获取空闲 slot，再 batch claim 最多这么多个任务。**slot-before-claim**，避免认领了任务却没有本地容量执行
3. **准备环境** — `runTask`（第 4336 行）：创建隔离 workdir、checkout repo、下载 skill bundle、写 execenv 上下文文件（CLAUDE.md/AGENTS.md 等），有 5min prepare timeout
4. **执行 agent** — 调 `server/pkg/agent` 的 backend（如 `claude.go`）spawn CLI 子进程，流式读取输出；同时 `watchTaskCancellation` 每 5s 轮询 server 看任务是否被取消/删除
5. **结果上报** — `complete`/`fail` + `ReportTaskMessages` + `ReportTaskUsage`（token 计费），走 detached terminal report（6min 超时，保证 daemon 重启也能上报）

**6 个后台 goroutine**（`Run` 第 1087-1094 行并发启动）：

- `heartbeatLoop` — 15s 发心跳，server 侧靠这个判断 runtime 是否存活
- `workspaceSyncLoop` — 发现用户新加入的 workspace
- `gcLoop` — 2h 扫描 `WorkspacesRoot`，清理已完成任务的 workdir（三种模式：full/orphan/artifact）
- `autoUpdateLoop` — CLI 自更新
- `tokenRenewalLoop` — PAT 续期，401 时提示重新登录
- `taskWakeupLoop` — 接收 WS 推来的任务唤醒，nudge poller 立即 claim（不用等下一个 poll 周期）

## daemon ↔ server 的两条通信通道

**① HTTP REST（控制面，`client.go`）** — 所有状态变更走这条：

- `Register` / `Deregister` — runtime 上下线
- `ClaimTasks` — batch 认领（`POST /api/daemon/.../claim`）
- `SendHeartbeat` — 15s 心跳
- `StartTask` / `CompleteTask` / `FailTask` — 任务状态机推进
- `ReportTaskMessages` / `ReportTaskUsage` — 流式消息 + 计费
- 30s 超时，有重试调度（`postJSONWithRetry`）

**② WebSocket（实时面，`wsrpc.go` + `daemonws/hub.go`）** — 低延迟通道：

- **task wakeup 推送**：server 有新任务时通过 `daemonws.Hub` 主动推给 daemon，不用等 poll 周期
- **WS RPC claim**：claim 走 WS 而非 HTTP，降低派发延迟；WS 不可用时自动 fallback 到 HTTP（但有 `errWSRPCUncertain` 保护，防止 fallback 导致 double-claim）

## server 侧的配合机制

server 收到 daemon 的 HTTP/WS 后，有四个组件协作维持状态正确：

- **`daemonws.Hub`**（`server/internal/daemonws/hub.go`）— 管理所有 daemon 的 WS 长连接，按 daemon_id + workspace_id 鉴权，推送任务唤醒
- **`runtime_sweeper`**（`server/cmd/server/runtime_sweeper.go`）— 每 **30s** 扫一次：runtime 超过 **150s** 没心跳 → 标 offline；offline 超过 7 天 → 删除；dispatched 超 5min → failed；queued 超 2h → 过期。这是 daemon 崩溃时的兜底
- **`heartbeat scheduler`**（`handler.NewBatchedHeartbeatScheduler`）— 批量聚合心跳写入 DB/Redis，避免每次心跳都打 DB
- **dispatch timeout** — dispatched→running 应该瞬间完成，5min 没变就是 daemon 出问题

## server/runtime（Open Agent SDK）的角色 —— 关键区分

这是最容易混淆的点。项目里有**两套并行的 agent 执行架构**：

|        | `server/pkg/agent`                          | `server/runtime`                            |
| ------ | --------------------------------------------- | --------------------------------------------- |
| 方式   | **CLI 子进程**（spawn claude/codex...） | **进程内 agent loop**（直接调 LLM API） |
| 依赖   | 用户本机装了对应 CLI                          | 只需 API key，无需 CLI                        |
| 使用者 | **daemon 实际用这套**                   | vendored 但**当前无代码引用**           |
| 定位   | 本地执行（daemon 模式）                       | 未来云 runtime（server-side 执行）            |

我 grep 过 `server/runtime` 的引用 —— **零引用**。daemon 的 `runTask` 走的是 `d.cfg.Agents[provider]` → `server/pkg/agent.New()` → 选 backend（claude.go/codex.go...）→ `backend.Execute()` spawn 子进程。

`server/runtime` 是 Open Agent SDK（`codeany-ai/open-agent-sdk-go`），提供 32 个内置工具、MCP 支持、permission 系统、hook 系统，全部在进程内跑。它存在于此是为**未来的云 runtime**铺路：当 server 自己就能跑 agent loop 时，就不需要用户本地装 daemon + CLI 了 —— 任务直接在 server 进程内执行。但目前这条路径还没接通。

所以当前的任务执行链路是：

```
server 派发任务 → WS wakeup → daemon pollLoop → batch claim
→ runTask 准备环境 → pkg/agent 选 backend → spawn CLI 子进程
→ 流式读取输出 → complete/fail 上报 → server 更新 issue 状态
```

`server/runtime` 是并行的、未激活的第二条路径。
