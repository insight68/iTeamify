# PRD：工作区积分计费本地化改造

状态：已获批，已完成本地实现；尚未生产部署或真实 Stripe 验收。日期：2026-09-03。

本方案替代 `prd-workspace-token-credits.md` 和 `docs/workspace-credit-cloud-contract.md` 中外部 Cloud 钱包、计费投递及准入架构；保留已确认的产品规则。部署与验收见 `docs/local-workspace-billing.md`。

## 1. 背景与目标

当前 Billing 是 Aurocreator 到外部 iteamify-cloud 的代理，钱包及 Stripe 履约不在本仓库。改为模块化单体：现有 Go 后端内的 Billing 模块、现有 PostgreSQL、Stripe Hosted Checkout。没有独立计费服务、第二数据库、消息队列或 Redis 钱包。

目标：同工作区共享余额；充值及累计用量重试不重复记账；余额与流水在同一数据库事务中保持一致；常规余额读取和任务准入不依赖外部 HTTP。

## 2. 产品边界

- 工作区拥有积分，用户仅为付款人/操作人；Owner/Admin 可以充值和查看订单及流水，普通成员只看余额及工作区使用量。
- 一次性美元预付费。充值金额可不同，但兑换比例全局一致，不赠送充值奖励，不设置套餐等级。
- 新建工作区一次性获得 1000 积分，无有效期；存量工作区不补赠，账号余额不迁移。
- 所有模型与 Token 类型统一使用 Admin 配置的积分费率；Agent、MCP 不单独收费。
- 保留全局软负余额下限：余额大于下限时允许新任务开始；已经运行的任务继续结算。该下限不是并发条件下的欠费硬上限。
- 不支持 BYOK、订阅、自动充值、折扣、积分转移、积分过期或批次抵扣。

## 3. 最小架构与数据

复用 Chi、sqlc、现有迁移器、task_usage、token_credit_rate 和 task_token_credit_rate_snapshot。按现有 service/handler/db 分层实现，不新增通用支付框架或多支付渠道接口。

新增四类表，名称在实施时按仓库现有约定最终确定：

| 数据 | 主要内容与约束 |
| --- | --- |
| 工作区钱包 | workspace_id 唯一、balance_micro、更新时间；每工作区一行 |
| 不可变积分流水 | workspace_id、增减值、业务类型、稳定业务键、来源/操作人、时间；业务键在工作区内唯一 |
| 充值订单 | workspace_id、payer_user_id、请求幂等键、美元 cents、积分 micro、兑换比例快照、Stripe Session/PaymentIntent 标识、履约状态和时间 |
| 全局充值设置 | 单例：美元兑换比例、允许的充值金额、负余额下限；变更审计复用现有机制 |

task_usage 增加累计已结算积分字段；不另建用量结算镜像表。Token 费率仍用已有版本表，不复制进新设置表。人民币、多币种或动态汇率不在范围。

计量全部采用整数：1 积分 = 1,000,000 microcredits，美元使用 cents；采用溢出检查。保留已实现的累计费用精度规则，UI 两位小数不改变账务精度。

流水显式保存工作区归属，不依赖 Agent/任务仍存在才能查账。工作区删除不得级联清除支付凭证；删除流程应拒绝未处理订单并保留账务审计记录。

## 4. 用户故事与验收

### US-001：获得正确的工作区余额

作为工作区成员，我希望所有成员看到同一个余额，切换工作区不串账。

- [ ] 新工作区创建事务内同时创建钱包和唯一试用流水，余额为 1000。
- [ ] 存量工作区初始化零余额，不补发、不迁移历史账号积分。
- [ ] 工作区切换与成员权限测试通过；读取不触发 Stripe 请求。

### US-002：安全地多次充值

作为 Owner/Admin，我希望每次付款准确且仅一次充值到购买时的工作区。

- [ ] 后端从当前身份解析工作区，客户端不能指定任意钱包或应得积分。
- [ ] 同一个创建请求重试返回同一订单；新的购买意图产生新订单。
- [ ] Session 创建调用使用订单级 Stripe 幂等键；超时不能盲目创建第二个 Session。
- [ ] Webhook 重复/并发/乱序、金额不一致和跨工作区查询测试通过。

### US-003：按真实累计用量消费

作为成员，我希望重复上报不会多扣，费率变更不会改写旧任务账单。

- [ ] 新任务开始时固定现有费率快照，不能等到首次用量上报才取费率。
- [ ] 本地事务内保存用量、累计已结算值、扣费流水及余额；任一步失败全部回滚。
- [ ] 累计值相同不写扣费流水；增加只扣差额；更小的乱序累计报告不覆盖已经接受的数据、不自动退款，并记录诊断信息。
- [ ] 多维度报告先归一化并拒绝重复维度；锁定顺序统一以避免死锁。

### US-004：余额不足与服务故障有明确行为

作为成员，我希望未运行任务遵守软负余额限制，已运行任务不被突然中断。

- [ ] 准入在任务进入 running 的事务边界检查本地钱包，不新增 HTTP 调用。
- [ ] 余额等于或低于下限拒绝新任务；数据库失败不能放行。
- [ ] Stripe 暂不可用只影响充值，不阻止已有积分消费。

### US-005：看到正式的计费页面

作为用户，我希望页面只显示余额、购买积分、流水、充值记录，而非接口调试信息。

- [ ] 保留 `/{workspaceSlug}/billing` 和工作区 React Query key；Web/Desktop 一起更新。
- [ ] 去掉端点说明、订阅 Portal、积分批次展示；统一错误和空状态。
- [ ] Usage 消耗显示两位小数、小号小数部分、不追加“积分”，下方小字显示剩余积分。
- [ ] Typecheck/lint 通过，接口 schema 及异常响应测试通过。
- [ ] 按 PRD 技能要求进行浏览器验证（dev-browser 未提供，使用可用 browser 技能执行）。

## 5. 功能与事务设计

### FR-1：充值创建

短事务固化订单及价格快照，提交后再调用 Stripe；不在数据库持锁期间发网络请求。请求身份、工作区和订单幂等键联合校验。Stripe metadata/reference 仅携带关联线索，不代替本地订单。成功/取消地址根据允许的站点根地址与已解析工作区生成，禁止任意外部回跳。

### FR-2：Webhook 履约

保留 `/api/webhooks/stripe`，后端直接验证原始请求体签名、测试/生产模式和预期事件类型。确认支付状态、订单、币种、金额、Session/PaymentIntent 匹配后，短事务内锁钱包、锁订单、幂等写入充值流水并增加余额，将订单标记已履约。

第一版只启用即时卡支付，不主动增加异步支付方式。绝不能仅凭 checkout.session.completed 名称就发积分；必须确认已支付。成功回跳仅查询本地订单状态。

提交后才返回成功；数据库暂时故障返回失败让 Stripe 重试。以订单唯一履约键防止不同 Event ID 造成双重到账，记录事件标识用于追踪。第一版不新增 Webhook 队列或独立事件消费服务。忽略无关的合法事件；验签或数据不匹配不可记账。为指定订单提供受权限控制的人工核验/补履约入口，调用相同幂等函数，不直接改余额。

### FR-3：本地用量结算

复用现有一次报告一次事务：先锁工作区钱包，在稳定顺序下处理任务用量维度，读取已结算累计值，计算正差额；保存用量/结算位置并写不可变流水，整个报告汇总后只更新一次钱包。所有计费入口遵守同一钱包优先锁顺序；事务内没有外部网络访问。

正常上报为累计值，不逐 Token 扣款，也不等任务结束才扣款。合法历史计量纠错不得借乱序上报自动退款，应以特权、幂等补偿流水处理。

### FR-4：读取与性能

余额按工作区唯一键读取；充值和流水以 workspace_id + created_at + id 索引进行游标分页，避免大 OFFSET。日常读取不 SUM 全部流水。Admin 兑换比例改动仅影响新订单，Token 费率改动仅影响新任务。

不同工作区各锁自己的钱包行；同工作区余额写入串行短事务。报告有行数/请求体上限。第一版不增加余额缓存、分布式锁或分区表。Usage 30 天积分总额明确按该期间的 usage 流水记账时间统计，确保与钱包扣款口径一致；Token 图表继续走现有计量数据，两者历史切换口径应有说明。

### FR-5：配置和故障边界

复用 `/etc/aurocreator/backend.env`：STRIPE_SECRET_KEY、STRIPE_WEBHOOK_SECRET；复用现有站点 URL。公钥当前无需使用。服务启动校验配置格式/配对，生产启用充值的部署验收缺少密钥应失败；关闭充值时余额、试用与用量结算仍可运行。不得因 Stripe 密钥缺失而静默关闭扣费。

普通成员只拿余额概要；订单、流水及创建支付保持 Owner/Admin 授权。日志不打印密钥、Webhook 原始载荷或完整 Checkout URL。

## 6. 切换与删除范围

1. 增量迁移新表和字段；不改写已应用迁移 472–488。所有索引使用单语句 CREATE INDEX CONCURRENTLY，不加外键或级联动作。
2. 停止旧计费 Worker，部署新结算路径。生产切换采用短维护窗口，不允许旧、新进程同时处理计费，不做钱包双写。
3. 建议从切换后启动的新任务开始计费：历史和切换时仍运行的任务只保留 Usage，不自动补扣。用持久化任务资格标记区分，不能每次按当前时间猜测；此项待用户确认。
4. 旧试用/用量 outbox 不重放进新钱包，不清空或销毁未审阅历史。停止写入/消费，确认无外部已付订单及余额后再单独清理其表；保留历史迁移文件。
5. Billing Handler 改为本地 service；现有公开 API 路径先保留，避免已安装客户端失效，但只对应同一个本地实现，不保留 Cloud 回退。Portal/批次旧入口明确停用，不回退外部服务。
6. 删除 WorkspaceCreditWorker、计费 outbox 运行代码及仅 Billing 使用的服务 Token 配置；保留其他功能使用的 Cloud Runtime 客户端与 Fleet URL。
7. 更新原 PRD/Cloud 契约为被替代状态；一次性工具清理作为独立变更，不与资金改造混在一起。

## 7. 非目标与必要运维

不做微服务、事件总线、双账本、积分批次、预占额度、多币种、自动退款或争议处理平台。退款/争议由人工处理，但上线前必须具备权限受控、理由留痕、业务键幂等的补偿记账流程，避免 Stripe 退款后积分不调整。人工操作先核对订单，禁止直接 UPDATE 余额。

提供只读账务核验：钱包余额等于积分流水合计；Stripe 已付订单必须有唯一履约记录。复用现有日志/监控报告支付失败、签名错误、结算失败，不额外建设监控平台。

## 8. 实施顺序和成功标准

1. 本地钱包与试用、用量事务、负余额准入及数据库并发测试。
2. Stripe Checkout/Webhook、订单修复路径与测试模式联调。
3. 接口/前端更新、管理员设置、部署配置预检与旧代码移除。
4. 增量迁移验收、切换清单、真实测试支付、Web/Desktop 浏览器验收。

- 同一订单并发履约 100 次，仅一笔充值流水和一次余额增加。
- 同一累计用量重放 100 次，仅一次实际扣费；累计增加只扣差额。
- 用量写入/流水/钱包任一步故障不产生半笔账；试用发放失败则创建工作区事务回滚。
- 跨工作区读取、订单 Session 猜测及伪造金额都失败。
- 同时充值和扣款无丢失更新；余额与流水合计一致。
- 钱包热点和多工作区分别压测，记录 p95/p99、锁等待及吞吐；不在未经测量时承诺固定延迟。
- 余额/准入的常规路径零 Stripe/Cloud HTTP 请求，分页读取不扫描整本账。
- 切换后旧数据不被补扣，已有任务不受中断；Stripe 故障不影响本地钱包消费。
