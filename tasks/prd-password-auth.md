# PRD：密码登录与注册流程优化

状态：用户已授权执行，第一阶段已完成本地实现；尚未部署。
日期：2026-10-11。

## 1. 设计时的背景与现状

以下是实施前的代码现状，作为设计依据保留；最终实现及验证见第 10 节。

- Web 与桌面端共用 `packages/views/auth/login-page.tsx`，当前仅有邮箱验证码及 Google 登录入口。
- `server/internal/handler/auth.go` 中的 `VerifyCode` 会查找或创建用户，现有邮箱入口合并了登录与注册。
- 验证码有效期为 10 分钟，每个邮箱 60 秒内限制重发，单个验证码最多尝试 5 次。当前验证码没有注册、登录、重置密码等用途区分。
- 登录后的 Web 流程已经处理安全的 `next` 跳转、待接受邀请、新用户引导与工作区目的地，应在此基础上统一衔接。
- `packages/views/settings/components/account-tab.tsx` 目前只提供个人资料管理，没有密码管理。
- 当前用户 JWT 默认有效期为 30 天，可通过 `AUTH_TOKEN_TTL` 配置。HTTP、WebSocket 及守护进程的 JWT 路径分别验证签名和声明，尚无账号级会话撤销校验。
- 移动端有独立的登录 UI、状态与安全存储，不能直接复用 Web/桌面端页面。

## 2. 目标

1. 设置密码的用户可在一个表单中完成邮箱密码登录，无需每次收取验证码。
2. 注册、首次设置密码、修改密码及忘记密码形成完整流程。
3. 保留老用户的既有账号、工作区、邀请和登录渠道。
4. 认证成功后的数据加载失败可以独立重试，避免让用户重复验证身份。
5. 重置密码后，旧的人类 JWT 会话与实时连接失效。

## 3. 第一阶段采用的选择

用户授权执行方案后，第一阶段采用以下选择：

- 默认展示密码登录，提供验证码登录切换与 Google 登录。
- 新版 Web/桌面端邮箱注册在验证邮箱后要求设置密码；Google 注册可直接继续。
- 老用户可继续验证码或 Google 登录，自愿补设密码，不阻断进入业务。
- 第一阶段覆盖 Web 与桌面端。旧版客户端及当前移动端保留已有验证码 API，因此“注册必须设置密码”暂时只适用于新版邮箱注册入口，不能宣传为所有客户端的全局规则。
- 若要求所有新账号都必须设置密码，必须同步调整移动端及旧客户端注册策略。
- 保留验证码登录意味着邮箱仍是一条完整登录渠道；密码与验证码是替代方式，不构成双因素验证。

### US-002：验证邮箱并注册

作为新用户，我希望清楚知道自己在创建账号，并完成邮箱验证和密码设置。

推荐流程：输入邮箱 → 验证邮箱 → 设置密码 → 完成注册并自动登录 → 原目标或新用户引导。

验收条件：

- [ ] 登录与注册有明确入口，切换时保留邮箱及安全的登录目的地。
- [ ] 验证邮箱后获得的证明只能完成该邮箱的注册操作，不提前签发完整登录 JWT。
- [ ] 账号创建、密码写入和注册证明消费在一个事务中完成；中途退出不会留下半完成的可登录密码账号。
- [ ] 已存在账号不能通过注册入口被覆盖密码；邮箱所有权验证后可引导到已有账号的登录/密码设置流程。
- [ ] Google 注册延续现有引导；关联到已有邮箱账号前必须检查可信提供方返回的邮箱验证状态。
- [ ] 关闭注册、邮箱及域名白名单规则继续生效。
- [ ] 旧版验证码 API 的兼容行为明确记录并回归验证。

### US-003：为现有账号设置或修改密码

作为老用户，我希望在不丢失已有数据的情况下增加密码登录。

- [ ] 修改成功后撤销旧的人类 JWT 会话，为当前已重新验证的客户端签发新凭证。
- [ ] 密码变更使用明确的提交按钮，不使用个人资料的自动保存机制。

### US-004：忘记密码后恢复登录

作为忘记密码的用户，我希望通过邮箱设置新密码并恢复访问。

推荐流程：输入邮箱 → 输入找回密码验证码 → 设置新密码 → 返回登录，保留邮箱和原目标。

验收条件：

- [ ] 对存在与不存在的邮箱返回一致的请求结果，并限制重复请求；不为不存在的邮箱创建账号。
- [ ] 找回验证码与登录、注册、首次设置密码的验证码不能互换使用。
- [ ] 验证码或后续操作证明短期有效，只能消费一次；并发提交也最多成功一次。
- [ ] 新请求使该用途的旧挑战失效，重置成功后使其他未完成的找回/密码变更证明失效。
- [ ] 重置完成后返回常规登录流程，发送密码变更通知。

## 5. 功能与技术要求

- FR-1：沿用 Go、sqlc 及现有 Cookie/Bearer 认证结构。共享 API、认证动作放在 `packages/core`，共享表单放在 `packages/views/auth`，Web/桌面端分别处理导航和凭证存储。
- FR-2：密码凭证建议存入独立的用户密码表，避免通用用户/成员查询读取密码哈希；字段名在实施时最终确定。API 不返回密码及其哈希。
- FR-3：密码使用 Argon2id 与随机盐，编码中保留算法及成本参数。最低成本参考 OWASP 的 19 MiB、2 次迭代、并行度 1，最终参数根据目标服务器基准确定，同时控制哈希任务并发。
- FR-4：按用户要求，密码长度为 10–128 个 Unicode 字符，允许空格、Unicode、粘贴和密码管理器；不强制大小写数字符号组合，不静默裁剪或 trim，拦截常见弱密码。第一期不对接外部密码泄露检测服务。
- FR-5：新操作挑战绑定邮箱、用途与具体挑战 ID，安全存储校验值，保留过期、尝试次数、发送状态及已消费状态。短验证码的存储应使用服务端密钥保护的校验值，避免裸快速哈希被离线穷举。
- FR-6：验证码验证后只签发有明确用途的短期操作证明；注册、首次设置密码及重置的最终写入原子消费该证明。旧端登录协议按 API 兼容边界保留。
- FR-7：邮箱和 IP 两级限流，必要时限制哈希并发。自托管未配置 Redis 时也必须有基本限流；配置 Redis 后采用可共享的计数，故障策略明确。
- FR-8：重发倒计时来自服务端的可重试时间。邮件发送失败不能显示“已发送”，且应提供明确的重试处理。线上缺少邮件服务配置时不得使用开发日志代替真实发送。
- FR-9：账号增加 JWT 会话版本。签发时包含版本，HTTP、WebSocket 及其他 JWT 鉴权入口都校验。密码修改/重置原子更新密码和版本；连接撤销与多实例缓存/通知失效纳入验证。
- FR-10：没有版本的历史 JWT 只在账号版本尚未变更时按初始版本接受；第一次密码变更后必须拒绝，以保留正常升级并防止撤销绕过。
- FR-11：账户密码状态由服务端提供，以 React Query 管理；密码和验证码仅保存在当前表单的内存中，不持久化，不写分析事件或日志。
- FR-12：新增/修改 API 使用 zod 与 `parseWithFallback` 解析，认证成功仍需检查必需字段，不能把回退空值当作有效登录结果；包含异常响应测试。
- FR-13：密码操作采用现有 CSRF 与传输防护。数据库迁移不添加外键；所有索引独立使用单语句 `CREATE [UNIQUE] INDEX CONCURRENTLY`。
- FR-14：新增 Web 路由遵循单词或名词/动词规则，例如 `/signup`、`/password/reset`；桌面端相关临时流程采用共享页面状态或 overlay，不新增不符合分类的前置路由。

## 6. 第一阶段边界

包括：密码登录、明确的注册入口、邮箱验证、老用户首次设置密码、修改密码、忘记密码、JWT 会话撤销、邮件与错误状态、登录后导航、旧客户端兼容。

暂不包括：手机号登录、Passkey、双因素认证、企业 SSO、设备会话管理列表、换绑邮箱、个人访问令牌或机器凭证批量撤销、营销首页整体重做。

## 7. 验证与指标

实施验收应分别记录：后端/事务/并发测试、共享 API/schema 与认证状态测试、Web/桌面端浏览器交互、320/390px 布局、旧客户端和移动端回归、真实邮件服务收发，以及部署后的验证。

最低场景覆盖：新邮箱注册、已有邮箱注册分流、未设置密码的老用户、密码错误、验证码过期/重发/多次错误、重复及并发消费、发送失败、重置后旧 HTTP/WS/JWT 拒绝、PAT 不受版本误伤、邀请与 `next`、CLI/桌面回调、认证成功后资源加载失败。

成功指标：已有密码的登录无需邮件等待；未验证邮箱不能完成新版密码注册；重复提交最多一次有效写入；重置后旧 JWT 无法访问；没有登录目的地丢失和老用户强制补设阻塞。上线后可统计注册完成率、各登录方式成功率和完成耗时，不在尚无基线时承诺提升百分比。

本次已实施代码、在临时数据库中应用迁移并完成本地验证。真实邮件、Google OAuth、桌面实机与线上验收尚未完成。详细记录见第 10 节。

## 8. 已采用的范围

1. 密码是默认登录方式，保留验证码切换和已配置的 Google 登录。
2. 新版邮箱注册先验证邮箱，再设置密码并自动登录。
3. 第一阶段覆盖共享 Web/桌面端流程；移动端和旧客户端保留原验证码协议。
